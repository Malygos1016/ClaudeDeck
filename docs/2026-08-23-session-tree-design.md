# CCTopBar 会话树设计（2026-08-23）

## 一、这份文档要解决什么

用户实报：fork 一个对话之后，顶栏上冒出三个标题相似的格子，**点哪个都没反应**。

查下来发现这不是一个 bug，而是四五个问题叠在一起，且暴露出一个更根本的事：
**顶栏现在的呈现模型（一个会话一个格子）与 Claude Code 的实际运行模型对不上。**
CC 早已不是"一个终端窗口 = 一个会话"，它有后台守护进程、有预热的备用进程、
有 fork 分叉、有可以 attach 的无窗口作业。顶栏还按老模型画，就必然画出
用户看不懂的东西。

本设计把顶栏的呈现模型改成**一个窗口一个格子**，并引入一棵会话树来表达
"这个窗口里到底有几个东西在跑、谁从谁分叉而来"。

---

## 二、现状实测（全部来自本机真实数据，不是推测）

用户 fork 之后，顶栏上那三个格子分别是：

| 格子上显示的字 | 会话 | 类型 | 真相 |
|---|---|---|---|
| `ClaudeDeck開發`（用户打的 tag） | `a9825e4f` | interactive | 真正持有终端窗口的主会话 |
| `Claudedeck本地安裝` | `8fbed941` | bg | 上一轮的后台作业，**已经干完了还赖着** |
| `Claudedeck本地安裝 ⑂ 我現在fork了，…`（整句话） | `042bab3b` | bg | fork 出来的、当前正在干活的那个 |

后来复查时 `8fbed941` 退出了，取而代之出现 `ba2319f2`，它的注册表里写着
`"spare": true`、没有对话文件、名字就是自己的编号——**这是 CC 预热的空壳进程**，
干等着接下一轮活，里面一句话都没有。

### 关键事实一：fork 出来的会话在系统层面没有窗口

追进程来源（`Win32_Process` 逐级向上）：

```
普通会话:   claude.exe ← powershell.exe ← WindowsTerminal.exe
fork 出来的: claude.exe ← claude.exe ← claude.exe ← WmiPrvSE ← svchost ← services.exe
```

fork 会话挂在系统服务底下，是脱离终端的守护进程。
**用户看到的那个窗口其实是父会话 `a9825e4f` 的窗口**，fork 之后 CC 把它的标题
改成了子会话的名字，造成"我在跟 fork 对话"的观感，但干活的进程在后台。

这条事实反过来支持了"按窗口合并"：父子本来就共用一个窗口，理应共用一个格子。

### 关键事实二：后台作业可以被接管，官方命令是 `claude attach`

`claude --bg "<task>"` 起一个后台作业后，CC 自己打印出这套命令：

```
claude agents             list sessions
claude attach <id>        open in this terminal
claude logs <id>          show recent output
claude stop <id>          stop this session
```

实测（起了一个一次性测试作业，测完已清理）：执行 `claude attach <id>` 后，
新终端标签出现，attach 客户端进程挂在 powershell 下，而**后台作业的守护进程
照常活着没被打断**。attach 只是把已经在跑的界面接到终端上显示，不重启、不打断。

这三个命令都**没有出现在 `claude --help` 的命令列表里**，属于隐藏子命令。
`claude agents --json` 可以脚本化列出活跃会话，但只给
`pid / cwd / kind / sessionId / name / status`，**不含 fork 关系，也不含窗口信息**。

### 关键事实三：点击失效有两个独立原因

其一，`kind == "bg"` 被前后端双重拦死：
`web/topbar.html` 给 bg 格子打 `data-bg="1"`，点击根本不发请求；
`app/routes/liveboard.py:44` 再补一刀 `409 "这是后台驻留会话,没有窗口可聚焦"`。
**这个判断的前提是错的**——bg 只说明它由守护进程驱动，不代表没有窗口可去。

其二，能发出请求的那个（`a9825e4f`）也必然失败。`app/focus.py` 靠比对窗口标题
文字找窗口，而 `_GLYPH_RE = ^[^0-9A-Za-z一-鿿]+` 只剥**开头**的符号：

```
正常窗口:  '✳ UE TALab倉庫配置位置'                    → 剥掉 '✳ ' 能匹配
用户的:    'Administrator: ◐ Claudedeck本地安裝 ⑂ …'   → 开头是字母，一个字符都剥不掉
实验开的:  '管理员: ATTACH-TEST'                        → 中文前缀，同样失败
```

同一台机器上英文 `Administrator: ` 和中文 `管理员: ` 两种前缀都会出现。
靠标题文字匹配这条路本身就是脆的，不该继续走。

## 三、设计

### 3.1 核心模型：一个窗口一个格子

顶栏不再按会话画格子，改为**按实际终端窗口**画。当前这个场景下，
`a9825e4f`（父）和 `042bab3b`（fork 出的子）共用一个窗口，合并成**一个**格子；
空壳 `ba2319f2` 不画；真正无窗口的后台作业不单独占格子，收进树里。

三个格子于是变成一个。

### 3.2 窗口归属怎么判定

**用进程链，不用标题文字。** 对每个会话进程逐级向上找父进程，遇到
`WindowsTerminal.exe` 即认定属于该终端；中间那层 `powershell.exe`（或其他 shell）
就是这个标签页的身份标识，同一个 shell 下的会话属于同一个标签。

进程链是系统级事实，不会因为窗口标题被改写而失效——这正是当前实现的软肋。

没有终端祖先的（守护进程）按下列规则归属：

- 有 `forkParentSessionId` 的，挂到父会话所在的窗口（fork 是就地发生的）
- 没有父的，视为真正的无窗口作业，进入"游离作业"分组

**待解决的技术点**：知道了 shell 的进程号之后，如何定位到对应的那个 WT 标签页
去激活它。UI 自动化拿到的标签控件其 ProcessId 是 WindowsTerminal 本身，不是 shell。
实现前需要先验证下列途径哪条可行，别直接开写：

1. UIA 标签控件上是否能取到关联的 shell 进程号（某些版本暴露在自动化属性里）
2. `wt.exe` 的命令行是否支持按会话定位标签（如 focus-tab 一类）
3. 退回标题匹配，但把它降级为**兜底**手段，并修好前缀问题（见 3.7）

### 3.3 树里显示什么

**只显示当前还开着的**（用户拍板）。已经结束的分叉不进树——树是"此刻这个窗口里
有什么在跑"的实时视图，不是历史档案。历史追溯由网页端的会话页负责。

树里排除两类：

- `spare: true` 的空壳进程（注册表里有这个字段，直接过滤）
- 已完成（作业状态 `done`）且不再需要用户介入的

无窗口的游离作业**藏进树里**，不单独占顶栏格子。

### 3.4 状态灯：冒泡，红 > 黄 > 绿

合并后的格子只有一盏灯，取窗口内所有成员的最紧急状态：

- 只要有任何一个在等用户输入 → **红**
- 否则只要有任何一个在忙 → **黄**
- 全都闲着 → **绿**

藏在树里的无窗口作业一旦卡住（作业状态 `blocked` / `needs` 非空），
**要让它所属的格子变红**。这是用户明确要的：藏起来可以，但卡住了必须看得见。

注意：作业的状态字段（`state` / `tempo` / `needs`）与会话注册表的状态字段
（`busy` / `idle` / `waiting`）是两套词汇，需要一张映射表。
`tempo: "blocked"` 或 `needs` 非空应当映射为 `waiting`（红），
当前实现完全没做这个映射，所以卡住的后台作业现在亮的是绿灯。

### 3.5 格子上显示什么名字

命名规则（用户拍板）：

```
<原会话的 tag 或标题> ⑂ <fork 后可自定义的部分>
```

前半截取父会话的 **tag**（用户自己打的名字，如 `ClaudeDeck開發`），
没有 tag 才退回标题。**前半截在 fork 会话里不可编辑**，要改得去父会话改，
改了之后所有子会话跟着变（它是引用，不是副本）。
fork 出来的会话**只能重命名叉子后面那一截**。

**必须截断**。CC 给 fork 会话的 `name` 直接就是**用户输入的整句 prompt**
（实测：`"Reply with exactly: TEST-OK. Do nothing else."`、
`"Claudedeck本地安裝 ⑂ 我現在fork了，如果我沒記錯的話，…"`）。
不截断的话一个格子就能撑爆整条顶栏、逼出两行模式，并且会把色带和飞块几何
一起带偏（顶栏色带宽度是按格子实际像素算的，见 DEVLOG 相应章节）。
截断后完整名字放进悬停提示。

### 3.6 点击行为

**点顶栏格子** → 激活该窗口（走 3.2 的进程链定位）。

**点树里的某一条**：

- 该条有窗口 → 同上，激活窗口
- 该条是无窗口的游离作业 → 开一个新终端标签执行 `claude attach <jobId>`

第二条已实测可行。实现上可以复用 `app/launcher.py` 现成的开 WT 标签逻辑
（包括它踩过的坑：必须用 claude.exe 全路径、必须净化 `CLAUDECODE` 等环境变量，
否则新进程会自认嵌套会话），只是把命令从 `--resume` 换成 `attach`。

**不要用 `--resume` 去接管还活着的会话**：CC 有并发检测，第二个实例会直接退出。
attach 才是正确姿势。

### 3.7 顺带必须修掉的

这几个是查证过程中确认的独立缺陷，与树无关但同属一条链路：

1. **过滤 `spare: true`**。空壳进程不该出现在任何界面上。一行判断的事，
   立竿见影少一个格子。
2. **窗口标题前缀**。若最终仍需标题匹配作兜底，`strip_glyph` 要能剥掉
   `Administrator: ` / `管理员: ` 这类前缀（不同语言不同写法），
   而不只是剥开头的装饰符号。
3. **`kind == "bg"` 不等于无窗口**。前端的 `data-bg` 拦截与后端的 409 拦截
   都要改成"先尝试定位窗口，确实找不到才提示"。
4. **已完成作业的退场**。作业 `done` 之后守护进程会滞留一段时间，
   期间仍被画成格子。应当按作业状态而非进程存活来决定是否显示。

### 3.8 数据从哪来

| 数据 | 来源 | 备注 |
|---|---|---|
| 活跃会话（pid/kind/status/name） | `~/.claude/sessions/<PID>.json` | 一个 PID 一个文件，只记一个 sessionId |
| 备用进程标记 | 同上的 `spare` 字段 | 现有代码未读取 |
| fork 父子关系 | `~/.claude/jobs/<id>/state.json` 的 `forkParentSessionId` | `app/live.py:132` 已读出，但只有后台作业面板用了 |
| 作业状态 / 卡住原因 | 同上的 `state` / `tempo` / `needs` | 需要映射到三色灯语义 |
| 窗口归属 | `Win32_Process` 进程链 | 本设计新增 |
| 接管 | `claude attach <jobId>` | 隐藏子命令，实测可用 |

官方的 `claude agents --json` 看似是权威接口，但它不含 fork 关系和窗口信息，
覆盖不了本设计的需要，只能作为交叉校验。

## 四、本设计不做的事

- **不做历史分叉树**。树只反映当下，历史归网页端。
- **不动 fork 的数据冗余问题**（见第五节），那是另一件事。
- **不改 CC 本身的行为**。CC 怎么起进程、怎么命名、怎么预热空壳，我们只适配，不干预。

---

## 五、另一条独立的问题线（本设计不处理，但需登记）

fork 会把父会话的**全部历史复制进新的对话文件**，由此产生：

- **搜索结果重复**：实测搜 `feasibility` 同时命中 fork 父（1163 条）与子（1263 条），
  内容大量重复，界面上没有任何"同源"提示。这直接打击 ClaudeDeck 的头号卖点。
- **起始时间被继承**：子会话的 `first_ts` 与父**完全相同**（都是 07-04），
  但它实际创建于 07-27、只活了 26 分钟，列表上看像横跨 23 天。
- **磁盘三份冗余**：父 18.6 MB + 子 18.4 MB + `jobs/<id>/tmp/parent-transcript.jsonl`
  19 MB ≈ 56 MB 存同一份对话，归档还会再镜像一遍。

后端 `indexer / scanner / archive / search` 目前**零 fork 感知、零内容去重**。
这条线要单独立项处理，不要塞进本次改动。

## 六、验证方式

沿用本项目既有纪律（见 DEVLOG「调试与验收方法论」）：

- **窗口归属判定**要覆盖多场景实测：普通会话、fork 父子、纯后台作业、管理员权限
  窗口、中英文两种前缀、两行模式。单场景通过不算数——本项目刚吃过这个亏
  （几何测量只在单会话下正确，多会话时错了一倍还看不出来）。
- **顶栏视觉**用 `CCTOPBAR_MOCK=rXyYgZ` 起真实实例，`PrintWindow` 取帧
  （GDI 截屏拍不到 WebView2 内容）。
- **页面内部状态**用 pywebview 探针窗口 `evaluate_js` 直接读，别靠目测截图估坐标。
  探针必须 `SetProcessDpiAwareness(2)` 且**不能隐藏窗口**（隐藏窗口 rAF 冻结，
  帧循环里的值会停在初值）。
- **接管**在一次性测试作业上验证，不要拿用户的真实作业做实验。

## 七、待确认

1. **WT 标签定位途径**（3.2 末尾列的三条），实现前必须先验证，否则整个
   "点击跳转"落空。这是本设计唯一的技术风险点。
2. 一个终端标签里先后跑过多个会话时（不是 fork，是用户自己连着开），
   格子上显示谁的名字？倾向显示当前活跃的那个，但未与用户确认。
3. 树的展开交互细节（悬停延迟、树的宽度上限、鼠标移出即收还是有停留宽限），
   等实现时看实际观感再定。
